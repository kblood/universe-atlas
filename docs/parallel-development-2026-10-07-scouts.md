## Scout bottlenecks
Read-only audit. Nothing was edited, no lock was taken and nothing was run except cheap reads (git log/diff, ls, grep over existing logs, CIM queries).

**Machine:** AMD Ryzen 9 9950X3D, 16 cores / 32 threads in two CCDs. 93.3 GB RAM, 66.9 GB of it free while a 50-step `test:work` from the tiers agent (pid 48352) held the slot. GPUs: an NVIDIA RTX 5090, plus an AMD Radeon iGPU that nothing uses today.

**Five mechanisms serialise development:**
1. The test slot: one machine-wide exclusive mkdir lock.
2. The GPU/browser lock.
3. The merge lock, held through the whole merge gate.
4. Quiet-machine cost runs: the fair protocol takes about 67 min, as 480 processes that each take the slot again.
5. Critical-path-bound suites: `test:full` takes 28.5 min, and a single 990 s test sets that length.

**Main finding:** the slot treats two different needs as one. Timing runs (`scripts/cost-fair`, `test:perf`) really do need the machine to themselves. Correctness runs only need a share of the CPU. Since 2026-10-07 every wall-clock assertion lives in `tests/perf` (the timing audit in `docs/test-policy.md`, and `docs/test-fixes-2026-10-07.md`), so correctness runs are designed not to depend on load. Yet `npm test` and `test:full` take the whole machine while using a small part of it:
- `npm test`: about 780–935 s of summed per-file time over about 110 s of wall time, so roughly 7–8 of 32 threads busy.
- `test:full`: an estimated 4,500 CPU-s over 1,707 s, so roughly 2.6 threads busy on average.

**Measured waiting** (counted from existing logs):
- Test slot: about 28,300 one-second wait lines across worktree logs, about 7.9 waiter-hours. The t6 worktree alone accounts for about 5.8 h.
- GPU lock: about 6.3 waiter-hours in main's logs.
- Specific incidents: the T6 fair run sat idle for 94 + 9 min, and a golden update waited 1.7 h and then failed on a busy port.

**Recommended order of fixes:**
- (a) Replace the binary slot with a reader/writer, CPU-token semaphore that serves waiters in FIFO order and keeps the never-nest token.
- (b) Split `test:full` into shards and reuse the tiers runner's longest-first scheduler.
- (c) Hold the merge lock only for the fast-forward of main, not for the gate.
- (d) Move fair cost runs into a scheduled exclusive window as one batch acquisition.
- (e) Make GPU-lock holds shorter. Take the golden cross-engine run (pure JS, no WebGL) off the GPU lock, after a check that the page really gets no WebGL.

**Warning:** when the tiers branch lands, it makes `test:pkg` always take the exclusive slot. That closes a real validity gap (audit F8), but without (a) a 2-second inner-loop test can wait behind a 28-minute `test:full` or a 67-minute fair run. (a) should land together with it.

No test pin, threshold or budget is loosened anywhere in these proposals.
