# deadtown optimisation survey and mapping onto the Universe Atlas hotspots

Read-only survey, 2026-09-29. deadtown = `C:\LLM\IWSDK\deadtown` (one git commit, `793bbdd`, so no perf history). Atlas = `C:\LLM\IWSDK\universe-atlas-rendering` (file:line refs are to that worktree, matching the perf plan).

## 0. Ground truth first (read this before trusting "performed well on Quest 3")

1. **There are no measured frame times anywhere in deadtown.** `orchestrator/logs/` and `orchestrator/research/` are empty; there is no before/after number in any doc, commit or STATE.json. The only quantitative artefact is `tools/perf-estimate.mjs`, a STATIC estimate (I ran it): 7x7 render ring = 49 chunks, 84 draw calls, ~119.8k triangles worst case (113k static chunk geometry), 2,224 trees, 56 buildings, 64 zombies. STATE.json says M10 (on-headset playtest) is still pending. `docs/webxr/quest3-perf-budgets.md` s7b says the Lambert/fog/radius wins were "measured on deadtown"; no numbers back that up. Treat every "effect" column below as UNMEASURED unless stated.
2. **deadtown is cheap by construction, not by clever optimisation.** Flat terrain (y = 0, no heightfield), 32 m chunks, forest = cone + cylinder (about 50 tris/tree, ~170 trees per forest chunk, only 13 of 49 ring chunks are forest at the origin), zombie cap 64, 20 Hz sim, no shadow maps, no textures (vertex colours, MeshLambert), 180 m far plane with fog. Several of the items on the requested checklist are **NOT implemented**: LOD mesh swaps, occlusion culling, greedy meshing, impostors/billboards, vertex-animation textures (plan parked, superseded), skinned meshes, crowd LOD, spatial hashing of zombies, time-slicing, workers for render work, shader warm-up, adaptive quality. LOD/occlusion/greedy-mesh are only a greenlit backlog (memory `project_deadtown_render_backlog`).
3. **The Atlas is already ahead of deadtown on most structural techniques** (workers for forest census/selection, ForestPatchBroadphase, ForestOrderedWorkIndex, forest-selection-cache, instance-update-ranges, terrain `leafRecords` + `sameFrame` cache at planet-renderer.ts:1184-1213, far atlas impostors, retained near/middle hysteresis at planet-forest.ts:~666). What deadtown offers is (a) a discipline (nothing in `update()` unless a key changed, no allocation, pooled everything) that the Atlas's fauna path violates, and (b) three or four cheap tricks. The honest mapping is short.

## 2. Mapping onto the Atlas hotspots

Budget/measured numbers are target-equivalent p95 from `desktop-perf-baseline-2026-09-29-contended.md` (native columns, host x1.7) against `desktop-perf-plan-2026-09-29.md`.

### 2.1 Fauna: 7-16 ms vs 1.4 (S1 paused 7.4 ms, turning 14.6 ms)

Atlas facts: `drawFauna` planet-renderer.ts:1553-1610; `FaunaFieldRenderer.submit` fauna-field-renderer.ts:64-94; cap `FAUNA_FIELD_CAPACITY=512`.

- Fauna costs 4.4 ms host even in the "ground paused" scenario. Nothing about the animals changes when the camera and the date are both still, yet the whole path re-evaluates every frame. deadtown's rule #1 (return early when the key is unchanged) applies but needs a two-level split: (a) world evaluation keyed on `worldNs` (per-member `faunaMemberActivityAtWorldNs`, `faunaPlace`), (b) view work keyed on frustum (cull, sort, rig selection). When paused, (a) is fully cached; when turning at constant date, only (b) reruns. deadtown does this split implicitly (sim tick vs render). **Concrete change:** memoise `{pose, grounded}` per member in an array keyed by `(worldNs, lifeOrigin version, ground-surface version)`, and reuse the previous frame's instance buffers untouched when the full key (adding a 1 m eye cell and turn-only frustum hash) is unchanged. Rendering-only; poses bit-identical to today because the cache returns what the pure function returned.
- Per-frame allocations (deadtown item 15). `drawFauna` allocates a `visible` array of object literals with a spread (`{cameraVisible,member,...grounded,...}`), a fresh `this.faunaDrawn=[]` with `position.toArray()` per animal, and per near-rig candidate `new THREE.Matrix4().compose(item.position.clone().sub(...))` plus a closure `ground:(x,z)=>...`; then `visible.sort(compareFaunaVisibility)` sorts every visible animal each frame. **Change:** preallocate `visible` as a struct-of-arrays pool (Float32Array positions, Int32Array member index, Float32Array distance), reuse candidate Matrix4s from a pool, hoist the ground closure to a method taking an index, and only fill `faunaDrawn` when diagnostics ask (the plan already lists this). Replace the full sort with a partial selection: only the nearest `faunaNear.capacity*2` need ordering (`nth_element` style); the far ones need no order except for budget dropping (currently rank-based at capacity 512).
- `FaunaFieldRenderer.part()` calls `this.color.set(colorString)` on every part of every animal every frame (fauna-field-renderer.ts:56); `Color.set(string)` parses CSS strings. deadtown precomputes its tints once (`archTint` Map<string,Color>, zombie.system.ts:222,257-270) and reuses a scratch Color. **Change:** cache `g.color`/`g.accentColor` as `THREE.Color` on the genome cache (`faunaGenomes` Map already exists) and use `setRGB`/`copy`. Trivial, safe, likely 10-20% of `submit`.
- Part-count per animal (about 30 `part()` calls each with two matrix ops) x up to 512 animals. deadtown's per-part-instanced approach has exactly the same shape and it only works there because the cap is 64 (about 700 part writes/frame). It does NOT scale to 512 and deadtown has no answer. The transferable design idea is deadtown's own parked VAT plan (bake to a texture, animate in the vertex shader), but the Atlas's animals are genome-parametric so per-genome bakes do not fit. Practical version: **crowd LOD by distance** (not in deadtown): beyond ~150-200 m submit a 3-4 part silhouette (torso+head+two leg slabs, no eyes/ears/horns/plates) with no gait phase; this is a new representation and needs the same "identity-preserving" digest test the plan demands, because it changes what is drawn (not canon).
- Herd-level frustum culling (plan item 5) already exists per herd only as a range test (`faunaHerdFrame`); add a herd bounding sphere vs frustum test before iterating members.

Does not transfer: deadtown's 20 Hz tick-decoupling. Atlas animal poses are analytic in `worldNs` and must be exact at a replayed date; evaluating poses on a stale 50 ms cadence would visibly differ from exact-date replay while time advances. It IS valid while time is paused (see the cache above).

### 2.2 Forest: 6-15 ms vs 1.6 (per-active-cell loop over ~5k cells, 48 ms selection-apply spikes)

Atlas facts: per-cell loop planet-forest.ts:629-687; `applySelection` planet-forest.ts:~127-140.

- **Still-frame early-out (deadtown #1).** The plan's item 1 is exactly deadtown's `if (cx === lastCx && cz === lastCz) return`. deadtown's version is the model: cheap integer key, no work and no allocation in steady state. **Change:** key on `(selectionRevision, workReference eye quantised to ~1 m, LOD-set-affecting flags, forward-vector quantised to ~0.5 degree)`; when unchanged skip the loop and `reconcileBatch`. Do not mutate placement, only skip re-deriving identical output.
- **Grace-band hysteresis (deadtown #2).** The Atlas already has ±12 m for near and 550/600 m for middle, so this is done; extend the same idea to the frustum test (a small angular margin) so slow turning does not flip membership, which is what forces the per-frame recompute during S2 (turning: forest 7.4 ms vs 6.35 paused).
- **Spatial-ring diff instead of whole-set re-apply (deadtown #2/#5/#8: per-chunk resources, only entering and leaving chunks are touched).** The 48-68 ms spikes are `applySelection` plus the queue rebuild replacing the whole selected set at once. deadtown's structure is one InstancedMesh pair per chunk, created/destroyed as the chunk key set changes. The Atlas's contiguous instanced batches make per-chunk meshes a poor fit for 5k cells, but the principle transfers as **diff-apply**: keep the previous `incoming` id set and touch only added/removed cells (the plan's item 2 says the same). `new Set(cells.map(...))`, `this.wanted.filter(...)` and the full-cache key scan are all O(selection) allocations on the main thread; reuse the worker-built typed arrays (already in `forest-selection-transfer.ts`) as the diff base.
- **Time-slice the apply.** deadtown does NOT do this (its chunk loads are synchronous and small by design), so nothing to copy; the Atlas's `ForestOrderedWorkIndex` is already the better mechanism. Note only that spreading spikes (plan item 8, rocks) is the fix, not shrinking the ring.
- deadtown's per-cell stateless hash placement (item 9) is what makes the Atlas's cell census pure too; already equivalent (canonical cell ids), no change.
- Far canopy/impostors and detailed trees: deadtown has no LOD/impostor, so nothing to borrow. Its 180 m far plane + fog is not applicable at planet scale.

### 2.3 Terrain: 5-12 ms vs 1.8

Already addressed by task 4a (`leafRecords`, `sameFrame`, planet-renderer.ts:1184-1213). deadtown adds nothing new to the CPU side. One applicable idea: **share the material across tiles** (deadtown #6). Each terrain tile builds its own `MeshStandardMaterial` with its own `onBeforeCompile` closure and per-tile uniform objects (planet-renderer.ts:780-822). They all share one program (identical `customProgramCacheKey`), so no recompile, but three re-refreshes material uniforms whenever the material id changes between consecutive draws; with a single shared material only per-object uniforms are re-sent. Feasible only if the per-tile values (`tileAnchor`, `patchTexels`, edge/morph, `pbrDetail`) move to per-mesh `onBeforeRender` writes or instanced/geometry attributes. Payoff is unmeasured and the plan already says "measure first"; deadtown gives no number. It also cannot be a straight copy: deadtown's single material has zero per-tile state.

### 2.4 Submission / overhead: 9-15 ms vs 4.8 (2048 PCFSoft shadow map every frame; unique tile materials)

- **Shadows: deadtown's answer is "no shadow map".** The Atlas keeps shadows (canonical look), so that is not directly copyable, but it confirms the cost class. main.ts:446-448 sets `autoUpdate=false` and then main.ts:4904 sets `renderer.shadowMap.needsUpdate=light.castShadow&&...` **every frame**, so the map is re-rendered every frame, including the forest depth passes and every terrain tile's `customDepthMaterial`. **Change (plan item 4):** set `needsUpdate` only when a key changes: sun direction quantised, light-camera frustum origin quantised to a texel-aligned step, and the caster set version (forest/fauna/rock batch revisions). deadtown's pattern of "recompute only when the bucket changes" (day-night.system.ts:128) is the same idea: for a sun that moves a fraction of a degree per real second at 1x world time, re-render every N frames or when the shadow-camera moved more than a texel. Expected payoff: submission drops by the shadow share (the profiler already attributes `shadow` via `systemTimer`); GPU passes drop too.
- **Casters:** deadtown sets `castShadow=false` on everything far/instanced; the Atlas already has `life-shadow-priority.ts`. Apply the same rule to the far canopy and to fauna beyond ~100 m (cast shadows from LOD1/impostor tiers is a plan item).
- Change-gated `instanceColor.needsUpdate` (deadtown #11: only if n > 0) is a small win for `FaunaFieldRenderer.endFrame`, which sets `needsUpdate` on 4 matrix and 4 colour attributes every frame even when count is 0.

### 2.5 GPU 34-39 ms vs 14.9 (terrain shader, far canopy, sky/ocean)

- deadtown's GPU lever list is Lambert instead of PBR, fog, smaller far plane, framebuffer scale 0.8, foveation. Only two map:
  1. **Framebuffer/render scale plus an adaptive tier (items 21, 25).** The plan already proposes a 3060 profile at ~0.75 scene render scale. deadtown's cookbook s7c gives a ready recipe: EMA frame time, 1 s hysteresis, drop at 95% of budget, raise below 65%, and "only rendering differs between tiers". This is the cheapest single GPU lever and is fully determinism-safe (render resolution only). Needs an upscale/composite pass since the Atlas is not XR; deadtown never solved the desktop case (its scale is XR-swapchain-only).
  2. **Cheaper lighting/shader tier for far terrain (item 7 in spirit).** The terrain fragment shader is the largest measured GPU cost (hide-terrain delta 5.9 ms x5.4 host at low100). deadtown demonstrates the payoff of the simplest lighting model but has no distance-dependent shader. Transfer as: far tiles (or below a screen-size threshold) use a variant with the PBR-detail texture taps and aerial-perspective work removed, chosen at tile creation (NOT by mutating `material.needsUpdate` at runtime; the cookbook warns this triggers a 50+ ms recompile). This changes rendering, not canon, but needs a visual-diff acceptance test.
- Far canopy (1.6 ms x5.4 GPU when hidden) and sky/ocean: deadtown has no counterpart (no impostors, no atmosphere). Fog does not transfer at planet scale.

### 2.6 The 1.4 s shader-compile freeze when the far canopy first appears

deadtown never handled this: it creates all materials up front in `init()` and never adds a variant mid-game, so it has no warm-up code (grep for `compile`/`compileAsync` returns nothing in either repo). The transferable principle is the cookbook rule "set up material variants at load time, not in the render loop". **Change:** at surface-ready (S0 `ready` ~5 s), call `renderer.compileAsync(scene, camera)` (or `renderer.compile`) with the far-canopy mesh and its `customDepthMaterial` present, or draw one hidden instance for one frame; verify three's `compile()` traverses invisible objects for the installed version before relying on it. Also check that the canopy material/program-cache key does not change between the warmed and the real state (planet-canopy/forest-impostor `customProgramCacheKey` includes version strings; a different key at first appearance would defeat the warm-up). Rendering-only; zero canonical impact. Measured freeze from the baseline: max frame 1.31-1.46 s in S6 descent.

### 2.7 What does NOT transfer

- Flat map / 32 m rectilinear chunks: deadtown's chunk-crossing keyed streaming, per-chunk merged meshes, and constant-y ground clamp all assume a flat, finite-scale world. The Atlas is spherical with floating-origin rebasing (`lifeOrigin`), so keys must be spherical cells and the origin version must be part of every cache key.
- Fixed-tick sim: deadtown's 20 Hz integer-mm sim is the source of determinism. The Atlas's determinism is an analytic pure function of the dated `worldNs` and canonical ids, and exact-date replay must not be perturbed. Do not step, quantise or interpolate canonical state; only cache pure results keyed on the exact inputs.
- Cap-based cheapness: zombie cap 64 vs 512 animals, 2,224 trees vs ~5k active cells with detailed families (LOD0 up to ~15k tris/tree per the plan). Per-part per-frame matrix writes work at 64, not 512.
- No LOD, impostors, occlusion, workers, time-slicing, shadow maps or textures exist in deadtown; nothing to borrow for those systems.
- Server AOI and prediction: not applicable.
- Vertex-colour-only shading: the Atlas look requires PBR/atlas textures.

## 4. Caveats on this survey
