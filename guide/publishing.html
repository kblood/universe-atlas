Atlas has its own repository inside the shared IWSDK workspace. Shared deployment scripts and site-shell sources belong to the parent workspace. Editing this guide in Atlas keeps it versioned with the game it describes.

What the build does

# From the universe-atlas directory
npm run dev
npm run build
npm run preview

The production build runs tsc --noEmit and then Vite. Vite follows the game, three lab entry points and guide chapters, bundles imported code and styles, and emits hashed assets. The configured base: "./" keeps asset references relative to the deployed project path.

The guide’s HTML remains readable without JavaScript. Its time explorer imports the game’s checkpoint definitions and bookmark encoder, so its “Visit this era” links use current date and version conventions.

A Vite plugin also emits a selected list of Markdown documents into dist/docs/ and publishes the project README. The chapter source links use these files. Raw src/ files and the complete repository are not exposed automatically.

Rapier is dynamically loaded for walking and isolated into its own large vendor chunk. Planet, drainage and river workers are built as runtime assets. After upload, the browser performs the procedural work; the public server needs no Atlas simulation process or generator database.

The two release paths

The public app target is dionysus.dk/webxr/IWSDK/universe-atlas/. The guide is published beneath it at guide/index.html. These are configured deployment destinations; this page does not report whether a particular local revision has already been uploaded.

# From C:\LLM\IWSDK — publish Atlas, its labs and this guide
.\release.ps1 universe-atlas

# Only when the shared IWSDK landing page also changes
.\release-site.ps1 -IndexOnly
  1. BuildThe project release script runs npm run build.
  2. Stagedist files and the applicable .htaccess upload over SSH/SCP to a fresh server folder.
  3. RotateThe existing live directory is renamed, then staging takes its live path.
  4. ServeApache serves the project over HTTPS from the cloud VM.

The script deletes the old project directory after successful promotion. Staging prevents serving a partially uploaded directory, but the successive rename commands are not a transactional swap: there can be a short gap, and a failed promotion can require manual recovery. The script does not retain a durable project rollback archive.

release-site.ps1 handles deploy/iwsdk-index.html and optional static page folders under the shared deploy/ directory. It preserves an index.html.bak copy before replacing the site index. Running only the site-index release does not publish Atlas’s new guide, because this guide belongs to Atlas’s dist/.

Serving and caching

The shared Apache configuration asks browsers to revalidate JavaScript, HTML and JSON. It also declares MIME types for WASM, KTX2 and glTF files. A project’s own built .htaccess takes precedence when present. Correct headers help avoid stale application files, especially in headset browsers.

HTTPS enables the public WebXR path. The live application is cloud-hosted static content and does not depend on the development workstation staying powered on. This is separate from other workspace tools that use a local backend or tunnel.

The game links to this guide from its action bar and help dialog. The guide links back to Atlas and to all three labs. A guide-only edit therefore ships with release.ps1 universe-atlas; the central landing page needs no update merely to make the in-game link work.

What a release check should establish

The build checks TypeScript and produces the complete website. A documentation smoke check should verify every chapter, shared stylesheet, source-document link, narrow-screen layout and era launch URL under the built directory.

Runtime validation is a separate layer. The repository includes catalogue and lifecycle unit tests, a cross-engine golden harness, direct-seek and visit-order acceptance tests, browser travel tests, terrain streaming tests, walking and river checks, and lab inspection scripts.

Existing browser checks can target a deployed URL through ATLAS_URL, with reports separated using ATLAS_RESULTS. Headset interaction and performance still need testing on the intended device. Historical validation documents record earlier runs; neither their existence nor a successful HTML build certifies every current subsystem.

For maintainers, the authoritative publishing instructions are the parent workspace’s DEPLOYMENT.md, release.ps1 and release-site.ps1. This chapter reflects those scripts as reviewed on 26 September 2026, including the distinction between project publishing and site-shell publishing.

Record the revision before publishing

Review and commit the intended changes before running the release script, then check that the working tree is clean. Record the commit with the release checks so the source for a published build can be recovered. The shared release script builds the current working directory; it does not create a commit or enforce a clean working tree automatically.
