# Desktop realism and procedural life: implementation plan

Date: 2026-09-27. Accepted direction; implementation started.

Published release `580936f` includes the canopy runtime through `98556a7`: complete canonical
patches and individual ownership, 5,500 m altitude prefetch, 3,500 m altitude
rendering, water-aware patch reuse, and retained terrain refresh during date
changes. The [integration record](canopy-runtime-integration-2026-09-28.md)
links the immutable RTX 5090 date-seek and flight/walking evidence; the
[deployment receipt](deployment-580936f-2026-09-28.md) records the live build
and byte audit. This does not complete realistic species assets or establish
midrange performance.
Baseline before this work: `27e89c897369270728e5ef4118dcc144e40af7fc`.

This is the current plan for planetary visual quality. It consolidates the
[proposal](desktop-realism-proposal-2026-09-27.md), the
[independent Opus 5.5 review](opus-5.5-desktop-realism-review-2026-09-27.md),
the [review assessment](desktop-realism-assessment-2026-09-27.md), and the
subsequent agreement on procedural trees and instance variation. Those review
records remain historical inputs. This document owns implementation order and
status; dated validation reports own measured results.

## 1. Product target

Desktop realism comes first. Aim for a believable landscape continuously from
orbit through atmospheric descent and low flight to walking. Forests, plants,
rocks and wildlife must exist during approach, with stable identities and
physical dimensions. Landing changes navigation/collision, not world content.
Clear weather must work; clouds cannot be the only way to conceal missing detail.

Quest will receive a separate measured quality profile. Proposed desktop target
is 1440p/60 FPS on a representative midrange gaming PC, with higher settings for
the development RTX 5090. Exact hardware floor and budgets remain open. No
current full-game measurements establish that target.

## 2. Content architecture

### Procedural species

Use the existing biosphere species/lineage identities and dated existence rules.
A species recipe defines trunk taper/curvature, branching rules, crown form,
leaf arrangement, density, bark and foliage palettes, and valid parameter
ranges. Physical allometry relates height, trunk thickness and crown width.
Animal recipes similarly conform to their existing genomes and body plans.

Recipes must describe coherent families. Variation within a species stays
recognizable; different species can have different structures. Habitat controls
distribution through moisture, slope, climate and substrate. Clustering, gaps,
undergrowth and size distribution contribute to realism alongside mesh quality.

Do not introduce a second independent species catalogue inside the renderer.
Current canonical forest candidates have identities and dimensions but are not
yet individually bound to complete dated plant species recipes. That binding is
an explicit future integration task, not something the current forest proves.

### Blender and assetctl

Blender authors detailed reusable components, templates and generation recipes:
trunks, branch structures, roots, foliage clusters, leaf shapes, bark and rock
surfaces, plus compatible animal rigs. Geometry Nodes can produce offline
variants. Exported geometry/material/animation data is usable at runtime;
Blender graphs are not automatically executable browser generators.

Use the repository assetctl boundary. Before expensive generation, validate an
asset brief specifying desktop target, metres, pivots, material/texture and LOD
budgets, visual criteria, provider, provenance and license. Preserve sources and
candidates; use `Assets/_assetctl/` for disposable review output. Export GLB with
matching LODs and appropriate compressed textures. Validate and package with
manifests. Model silhouettes, UVs and deformation quality remain acceptance gates.

### Bounded structural variants

Create/cache a bounded set of structural variants per resident species: different
branch arrangements, crown shapes and age/damage forms. Eight variants is an
initial experiment, not a fixed global budget. Cache keys include species,
recipe/asset version, variant and LOD. Evict by explicit memory budgets.

Assemble compatible modules or generate branch geometry in bounded worker jobs;
cache completed meshes for instancing. Avoid a separate scene object per branch.
Use one resident asset family in the first landscape before scaling to many
species. Structural changes require different cached geometry; recolouring does
not. Matching LODs preserve physical dimensions and crown silhouette.

### Per-instance variation

| Parameter | Representation | Constraint |
| --- | --- | --- |
| Position, yaw and physical size | Instance transform | Owned by canonical individual, camera independent |
| Bark and foliage tints | Separate instance colours with material masks | Shared material, species-constrained palette |
| Crown width, lean and bend | Controlled vertex deformation or compatible morphs | Correct normals, culling bounds, shadows and LOD |
| Bark/leaf surface variation | Atlas selection or texture coordinates | Shared compatible texture/material resources |
| Wind response | Shared field, individual stiffness/phase | Root anchored, bounded date-addressable phase |
| Seasonal appearance | Species/environment/date parameters | Respect lifecycle and signed BigInt time |

Colour/shape variation should not require a unique material for every tree.
Instancing reduces submissions, not vertex, fragment, overdraw or shadow costs.
Many topology variants and materials can still fragment batches. Measure the
tradeoff between diversity, cache size and rendering cost.

## 3. Identity, time and physical scale

- Preserve current seed/body/cell identities, positions, heights and yaw during
  the initial renderer work. A new placement distribution requires an explicit
  population version and compatibility decision.
- Derive species recipes from species identity; structural variant and
  individual parameters from stable individual identity. Camera, cache contents,
  task completion order and visit order must never choose these values.
- Distinguish identity versions (world/population/history) from appearance
  versions (assets/material/representation). Pixel baseline keys include both.
- A future growth/generation index must respect species birth/extinction and
  body lifecycle. Use bounded random-access queries for dates; do not simulate
  all preceding time. Handle negative dates with deliberate floor/modulo rules.
- Roots remain at canonical ground contact. Species dimensions constrain mesh
  scale, collision proxies, culling bounds and canopy summaries.
- Fix or explain existing history/version compatibility failures before adding
  new identity version axes. Renderer-only changes do not silently reseed worlds.

## 4. Continuous forest and terrain representations

| Scale | Intended representation |
| --- | --- |
| Near | Detailed branches, leaves, trunks, ground cover and contact shadows |
| Middle | Simpler meshes or relightable impostors preserving individual form |
| Far | Aggregate canopy preserving crown coverage, height and colour |
| Regional/orbital | Terrain/canopy appearance derived from the same ecological field |

Initially derive aggregate coverage from the existing population rules and
bounded regional summaries. Do not invent dense far forests that resolve into
sparse near trees. Avoid drawing both representations at full coverage during
handoff. Treat ground and canopy height separately; trees must not become solid
collision terrain. Evaluate parallax, lighting and silhouettes in clear weather.

Use projected size/error and hysteresis for LOD, with physical distance and
memory limits. Forward prefetch may prioritize work but cannot move the visible
dense forest area when the camera rotates. Resident regions use stable origins
and retained instance buffers. Change only dirty instance ranges. Later spatial
chunking must handle both view visibility and off-camera shadow casters.

Existing terrain already supplies adaptive tiles, horizon culling and local
surface detail. Improve rock/soil/wetness material response and metre-scale
features without adding an unversioned terrain height field. GPU grass patches
are a candidate for dense cover; occupancy remains consistent with the world
query and tile height data.

## 5. Lighting, atmosphere, clouds and frame budget

Establish a common sun/sky, aerial perspective and exposure contract across
terrain, trees, fauna, water and clouds. Terrain already uses PBR; current tree
and animal materials are simpler. Evaluate foliage transmission and coherent
roughness/normal detail under the common lighting baseline.

Audit the RGBA16F cloud scene capture, which currently has no requested MSAA.
Compare bounded MSAA/depth-resolve and post-AA approaches before choosing leaf
coverage techniques. Any shader deformation must be reflected in shadow/depth
passes. Logarithmic depth is enabled; measure its cost before changing depth
architecture. Keep current full-resolution desktop clouds as the baseline while
investigating the earlier reduced-resolution checker artifact.

Start with one bounded local sun-shadow region, then evaluate cascades and far
terrain shadow approximations. A shared atmosphere LUT implementation is a
candidate follow-on, not a prerequisite for all useful improvements. Stay on
WebGL2 until a measured bottleneck warrants an independently scoped migration.

Measure full-game CPU, GPU, uploads, draws, triangles, JS heap and estimated GPU
memory. Track distributions and cold/warm streaming separately. Reserve costs
for terrain, vegetation, fauna, water, shadows, clouds, UI and headroom. Existing
416 MiB accounting is incomplete driver/browser accounting, not a certified
desktop asset budget. Expand budgets deliberately with measurements.

## 6. Animal realism

Start with one continuous, rigged body plan compatible with existing genome
proportions, then expand. Bind bone lengths/morphs to the genome; authored rigs
must support realistic deformation. Keep exact-date movement and individual IDs.
Investigate deterministic paths with bounded segment/corridor obstacle checks,
stable interval boundaries and fallbacks. Foot contact requires reach limits,
ground normals and stance timing, not merely body-height adjustment.

Profile conventional skinning before adopting instanced bone palettes or baked
vertex animation. Keep the current 128-animal budget until evidence supports
more. Structural diversity must not come from disconnected anatomy.

fast traversal, stationary camera rotation and replay after cache eviction.

- Individual identities, dimensions and placement survive approach and A→B→A.
- Turning in place does not move the full-density forest footprint.
- A warmed stationary view does not repeatedly upload unchanged tree matrices

# Local detailed-tree forest integration

_Development-worktree status, 2026-09-28. The opt-in integration passes focused CPU/loader and one RTX 5090 browser fixture; it is not the published forest default or visual/performance acceptance._

## What the local path does

The forest can asynchronously load a supplied two-LOD tree asset family into
its near and middle instance batches. The browser fixture enabled optional
leaf transmission at 0.35. The path keeps canonical population cells,
habitat decisions, positions, and 10–22 m population-height range as the source
of truth. The family loader checks for forest coverage and conservative bounds;
the previous representation remains available if a load fails or becomes
obsolete.

Tree eligibility comes from the dated species catalogue already passed from
the biosphere. The catalogue binds stable cell identities to species and
derives deterministic per-instance appearance. The detailed path currently
accepts branching recipes; spire and unbound cells continue to use the legacy
forest representation. Each supported cell gets one supplied geometry per
LOD, with separate bark and foliage brightness tints, the family wind phase,
dated wind updates, and foliage coverage carried to the depth/distance
materials. The existing population height scales the supplied model; this
does not yet provide species-specific physical dimensions or multiple
structural variants.

The entry point is the development-only `window.__atlas.loadForestTreeAssets`
hook after visiting a planet. The loader can attach the same local
aerial-perspective inputs used by terrain, using the retained forest frame;
when requested, this is installed before the optional leaf-transmission hook.
Obsolete asynchronous results are discarded after the loader finishes;
texture or decoder work is not aborted. Immersive rendering continues to use
the legacy path. No new family asset is loaded by default in the published
application.

## Limits and current status

This integration covers only detailed near/middle trees. The distant canonical
canopy still uses the legacy faceted shape, so its silhouette can disagree
with the supplied tree family. Mixed batches still submit legacy geometry for
cells drawn by detailed geometry. Shadow behavior, off-camera casters, and the
resulting vertex cost need measurement. There is one structural geometry
choice per LOD; per-species dimensions, a richer palette, bounded structural
variants, and an asset resource cache are not yet connected. This work does
not demonstrate complete-canopy visual continuity, accepted realistic species
assets, XR readiness, or a general performance improvement.

## Reuse the current material and texture paths

The native foliage GLB uses an alpha-masked `MAT_AtlasFoliage` texture with a
positive cutoff (currently 0.5). `loadTreeAssetFamily()` already exposes
`foliageCoverage: 'mask' | 'hash'`: the default preserves alpha testing; the
existing `hash` option sets `alphaTest = 0` and enables Three.js `alphaHash` on
the foliage material. The instanced batch copies the alpha-test/hash settings
to its custom depth and distance materials. Compare these two modes first on
the same family-F GLB, without changing geometry or the authored alpha image.

The initial [hash diagnostic](../test-results/three-ez-impostor-reference/native-map-fix/alpha-hash-followup.json)
tests that existing option on a cloned material at three views. At the front
32 px output, hashed foliage gives 300 weighted tree pixels against 280.02 in
its high-resolution reference; the ordinary mask gave 38. The two
high-resolution representations differ by only 0.28–0.31% mean absolute alpha
across the tested views. This remains static coverage evidence; the later
isolated test measures date and yaw changes. HASH is still a lab option, not a
game setting.

Add two isolated material/texture trials to that comparison:

1. **Alpha-to-coverage:** keep the 0.5 alpha test and set
   `material.alphaToCoverage = true` for the colour draw. Three.js enables
   `SAMPLE_ALPHA_TO_COVERAGE` for that material and smooths the cutout edge
   with `fwidth`; its docs require an MSAA-enabled WebGL context (renderer
   created with `antialias: true`). The current main and tree labs request
   antialiasing, but record the actual context's antialias attribute and
   effective sample state for every run. Do not assume a requested context
   gives a useful sample count on every device. For an offscreen render target,
   canvas antialiasing is insufficient: the target itself needs a verified
   positive sample count and a multisample resolve. The current comparison's
   native probe targets have zero samples, and the cloud scene target has its
   own AA setting. Alpha-to-coverage smooths
   fractional edge coverage; it does not restore alpha coverage already lost
   while making smaller mip levels. Keep the alpha test and existing depth
   behavior, and inspect colour/depth/shadow edges together. `createBatch()`
   currently copies alpha-test/hash settings, but not `alphaToCoverage`, to
   its custom depth and distance materials; treat this first as a colour-pass
   experiment and record the resulting shadow edge instead of implying matched
   multisample shadows.
2. **Coverage-preserving mip chain:** make a test-only mip chain from the exact
   embedded foliage PNG. Downsample alpha, then for every level find the alpha
   remap that preserves the base level's fraction of texels above the GLB's
   0.5 cutoff. Filter RGB in linear light with alpha weighting to avoid dark
   RGB leaking from transparent texels, then encode it back to sRGB. The
   current Three.js `Texture.mipmaps` upload path accepts an explicit level
   array, including the base image, when `generateMipmaps` is false; use a
   lab-only texture copy so the source GLB and shipped default stay unchanged.
   Compare coverage-preserving mips alone first; test it combined with
   alpha-to-coverage only if the individual results justify the extra mode.

For Atlas's leaf atlas, also measure coverage within each leaf cell. Preserving
only the whole texture's average could conceal losses in a sparse cell while
increasing coverage in a denser one. This is a test requirement for the adapter,
not a claim that the current textures have such a mip chain.

`alphaHash` trades hard cutout edges for a stochastic threshold. The corrected
isolated comparison measures increased coverage variation under 0.5° yaw
steps and at the moving wind date relative to its downsampled sample; it does
not establish whether that pattern is perceptually acceptable. Atlas does not
use a general TAA resolve in this tree path.

The offline method is established: Ignacio Castaño's original alpha-mipmap
method solves for a per-level remap that preserves coverage at a chosen alpha
reference. Current DirectXTex `texconv` still exposes `--keep-coverage <ref>`.
However, Atlas's tree authoring operation validates embedded 8-bit PNGs, and
the local `assetctl texture` KTX2 command generates ordinary mips with
`toktx --genmipmap`; it has no coverage-preservation option. A DirectXTex DDS
chain is therefore a useful offline reference, not a drop-in tree artifact.
The smallest initial test is to feed precomputed levels to the lab's Three.js
texture copy. Changing the tree exporter/GLB texture contract is a separate
decision after the visual comparison.

## Keep impostor atlas bleed as a separate issue

The Three.ez baseline packs 16 × 16 capture views into one texture atlas and
lets the renderer generate mips for the whole atlas. Ordinary whole-image
downsampling mixes adjacent view cells at coarse levels; bilinear samples can
also cross a cell edge without guard texels. This can cause repeating colour
and alpha coverage from neighbouring views. It is separate from foliage alpha
coverage loss on the native mesh.

If the native-resolution Three.ez comparison still justifies that renderer,
test per-cell mip generation with edge dilation/gutters and cell-clamped UVs
as an atlas-specific follow-up. Do not use its larger 32 px weighted area as
evidence that the native mesh's alpha mip chain is fixed.

Use the same hash-verified family-F near GLB, material, light, exposure, camera
direction and date for the remaining alpha-to-coverage and
coverage-preserving-mip trials. MASK and HASH have been compared in the

- alpha-weighted coverage and binary coverage at the authored 0.5 threshold;

# Desktop canopy: local integration and acceptance

The complete canonical census now feeds the desktop planet renderer. The current
build includes the canopy runtime through `98556a7`; the dated checkpoints below
preserve earlier implementation evidence. The cited checks are production-preview
evidence, not a deployment claim or completion of the desktop realism plan.

## Structure

- A worker selects conservative patches within 4.5 km, then samples the existing
  terrain and habitat rules. One request contains at most 64 complete patches.
- The host installs whole patches within a soft 2 ms / 512-slot frame budget.
  A contiguous allocator caps residency at 229,376 trees; capacity failures keep
  the existing fallback. Empty completed patches are distinct from pending work.
- Near meshes and far ray-intersected proxies share tree identity, physical
  shape, placement and an integer pixel coverage hash. A separate Uint16
  ownership attribute transfers each admitted tree at 550–600 m with hysteresis.
- Static attributes retain a metre-based local origin. Rebases are prepared in
  slices and swap the position buffer and origin together. Water generations
  invalidate pending replies while preserving useful installed patches.
- The new path is desktop only. XR retains the previous representation pending
  dedicated stereo acceptance. Current legacy faceted trees remain placeholders
  for the species asset stage.

/** Screen-door coverage changes visibility without shrinking a physical tree.
 * alphaHash preserves opaque depth testing and avoids sorted transparent forests. */
function forestMaterial(vertexColors:boolean){
  const material=new THREE.MeshLambertMaterial({vertexColors,color:vertexColors?0xffffff:0x456c28});
  material.onBeforeCompile=shader=>{
    shader.vertexShader='attribute float instanceCoverage,instanceForestSeed;\nflat varying float vForestCoverage,vForestSeed;\n'+shader.vertexShader;
    shader.vertexShader=shader.vertexShader.replace('#include <begin_vertex>','#include <begin_vertex>\nvForestCoverage=instanceCoverage;vForestSeed=instanceForestSeed;');
    shader.fragmentShader='flat varying float vForestCoverage,vForestSeed;\n'+forestCoverageGLSL+shader.fragmentShader;
    shader.fragmentShader=shader.fragmentShader.replace('#include <alphahash_fragment>',`#ifdef USE_ALPHAHASH
      diffuseColor.a *= vForestCoverage;
      #include <alphahash_fragment>
      #else
      if(atlasForestHash(uint(vForestSeed+.5))>=atlasForestLevel(vForestCoverage))discard;
      #endif`);
  };
  material.customProgramCacheKey=()=>`forest-coverage-2/${vertexColors}`;return material;
}

function readGLB(buffer:ArrayBuffer):GLBDocument {
  const view=new DataView(buffer);
  if(buffer.byteLength<28||view.getUint32(0,true)!==0x46546c67||view.getUint32(4,true)!==2||view.getUint32(8,true)!==buffer.byteLength)throw new Error('Expected a complete glTF 2 GLB');
  const length=view.getUint32(12,true),start=20+length;
  if(view.getUint32(16,true)!==0x4e4f534a||start+8>buffer.byteLength||view.getUint32(start+4,true)!==0x004e4942||start+8+view.getUint32(start,true)!==buffer.byteLength)throw new Error('Expected JSON and embedded binary chunks');
  const json=JSON.parse(new TextDecoder().decode(new Uint8Array(buffer,20,length)));
  if(json.buffers?.length!==1||json.buffers[0].uri||json.extensionsRequired?.length)throw new Error('Only self-contained author-6 GLBs are supported');
  if(json.nodes?.length!==1||json.nodes[0].mesh!==0||['matrix','translation','rotation','scale'].some(k=>json.nodes[0][k])||json.meshes?.length!==1||json.meshes[0].primitives?.length!==2)throw new Error('Expected one untransformed two-material tree');
  if(json.materials?.length!==2||json.materials[0].name!=='MAT_AtlasBark'||json.materials[1].name!=='MAT_AtlasFoliage'||json.images?.length!==4)throw new Error('Expected author-6 bark and foliage');
  if((json.materials[0].alphaMode??'OPAQUE')!=='OPAQUE'||json.materials[1].alphaMode!=='MASK'||(json.materials[1].alphaCutoff??.5)<=0)throw new Error('Tree foliage requires alpha MASK with a positive cutoff');
  const formats:Record<string,string>={_WIND:'SCALAR',_BRANCH_LEVEL:'SCALAR',_LEAF_CENTER:'VEC3',_LEAF_PIVOT:'VEC3',POSITION:'VEC3',NORMAL:'VEC3',TEXCOORD_0:'VEC2',TANGENT:'VEC4'};
  for(const [index,p] of json.meshes[0].primitives.entries()){
    if(p.material!==index||p.mode!==undefined&&p.mode!==4||p.targets||Object.keys(p.attributes??{}).length!==8||!Object.keys(formats).every(k=>Number.isInteger(p.attributes?.[k])))throw new Error('Incomplete tree vertex contract');
    const count=json.accessors[p.attributes.POSITION]?.count;
    for(const [name,type] of Object.entries(formats)){
      const a=json.accessors[p.attributes[name]];
      if(!a||a.type!==type||a.componentType!==5126||a.normalized||a.sparse||!Number.isInteger(count)||count<1||a.count!==count)throw new Error(`Invalid tree accessor ${name}`);
    }
  }
  return {json,binary:new Uint8Array(buffer,start+8,view.getUint32(start,true))};
}
function imageBytes(doc:GLBDocument,index:number){
  const image=doc.json.images[index],view=doc.json.bufferViews[image.bufferView];
  if(image.uri||image.mimeType!=='image/png'||!view||view.buffer!==0||!Number.isInteger(view.byteLength)||view.byteLength<=0)throw new Error('Expected an embedded PNG');
  const start=view.byteOffset??0,end=start+view.byteLength;
  if(start<0||end>doc.binary.length)throw new Error('Image outside GLB binary');
  return doc.binary.subarray(start,end);
}

            }

          },

        };
      },
      dispose(){if(disposed)return;if(activeBatches)throw new Error('Dispose tree batches before their family');disposed=true;dispose();},
    };
  }catch(error){dispose();throw error;}

/** This snapshot receives the already dated catalogue from main. It neither
 * invents species nor evaluates a second date or lifecycle model. */
export function forestTreeCatalogue(species:readonly Species[]){
  const trees=species.filter(s=>s.kind==='tree'&&(s.family==='branching'||s.family==='spire')).slice().sort((a,b)=>a.id.localeCompare(b.id));
  const recipes=new Map(trees.map(s=>[s.id,treeSpeciesRecipe(s)]));
  if(recipes.size!==trees.length)throw new Error('Duplicate dated tree species');
  const signature=JSON.stringify([...recipes.values()]);
  return {signature,count:trees.length,
    resolve(cellId:string){
      const species=bindTreeSpecies(cellId,trees);if(!species)return null;
      const recipe=recipes.get(species.id)!;
      return {recipe,appearance:treeInstanceAppearance(recipe,cellId)};
    },
  };
}
export type ForestTreeBinding=NonNullable<ReturnType<ReturnType<typeof forestTreeCatalogue>['resolve']>>;

import type {Species} from './biosphere-model.ts';

/** Presentation contract only: never part of canonical surface-cell addresses. */
export const TREE_RECIPE_VERSION='tree-recipe-1';
export const TREE_VARIANT_COUNT=8;
export const TREE_ASSET_VERSION='temperate-branching-v1';

export type TreeSpeciesRecipe=Readonly<{
  version:typeof TREE_RECIPE_VERSION; speciesId:string; lineageId:string;
  family:'branching'|'spire'; sourceFingerprint:string;
  heightM:number; crownWidthM:number; trunkDiameterM:number;
  branchCount:number; branchAngleRad:number; curvature:number;
  leafLengthM:number; leafWidthM:number; leafDensity:number;
  barkSRGB:string; foliageSRGB:string;
}>;

function hash(text:string){
  let h=2166136261;
  for(let i=0;i<text.length;i++){h^=text.charCodeAt(i);h=Math.imul(h,16777619);}
  h^=h>>>16;h=Math.imul(h,0x7feb352d);h^=h>>>15;h=Math.imul(h,0x846ca68b);
  return (h^(h>>>16))>>>0;
}
const unit=(...parts:unknown[])=>hash(JSON.stringify(parts))/0x100000000;

/** The caller supplies the already dated/eligible catalogue species. Rendezvous
 * assignment is independent of enumeration order and unrelated non-tree species.
 * Adding a tree species can transfer some assignments; it does not move cells. */
export function bindTreeSpecies(cellId:string,eligibleSpecies:readonly Species[]):Species|null {
  if(!cellId)throw new Error('Canonical cell id is required');
  let chosen:Species|null=null,best=-1;
  for(const species of eligibleSpecies){
    if(species.kind!=='tree'||(species.family!=='branching'&&species.family!=='spire'))continue;
    const score=hash(JSON.stringify([cellId,species.id,'tree-species-binding-1']));
    if(score>best||(score===best&&species.id<(chosen?.id??''))){chosen=species;best=score;}
  }
  return chosen;
}

/** Convert existing catalogue traits into a physical rendering envelope. The
 * trunk/crown relationship is an art heuristic, not a botanical simulation. */
export function treeSpeciesRecipe(species:Species):TreeSpeciesRecipe {
  if(!species.id||!species.lineageId)throw new Error('Catalogue species and lineage ids are required');
  if(species.kind!=='tree'||(species.family!=='branching'&&species.family!=='spire'))throw new Error('A catalogue tree species is required');
  const t=species.traits;
  for(const key of ['heightM','widthRatio','branchCount','branchAngle','curvature','leafLength','leafWidth','leafDensity'] as const)
    if(!Number.isFinite(t[key]))throw new Error(`Non-finite tree trait ${key}`);
  if(t.heightM<=0||t.widthRatio<=0||t.leafLength<=0||t.leafWidth<=0||t.branchCount<1||t.leafDensity<0||t.leafDensity>1)throw new Error('Invalid tree physical envelope');
  if(!/^#[0-9a-f]{6}$/i.test(t.color)||!/^#[0-9a-f]{6}$/i.test(t.woodColor))throw new Error('Tree colours must be sRGB hex');
  const source=[species.id,species.lineageId,species.family,t.heightM,t.widthRatio,t.branchCount,t.branchAngle,t.curvature,t.leafLength,t.leafWidth,t.leafDensity,t.color,t.woodColor];
  return Object.freeze({version:TREE_RECIPE_VERSION,speciesId:species.id,lineageId:species.lineageId,family:species.family,
    sourceFingerprint:hash(JSON.stringify(source)).toString(16).padStart(8,'0'),
    heightM:t.heightM,crownWidthM:t.heightM*t.widthRatio,
    trunkDiameterM:t.heightM*(species.family==='spire'?.026:.034),
    branchCount:Math.round(t.branchCount),branchAngleRad:t.branchAngle,curvature:t.curvature,
    leafLengthM:t.leafLength,leafWidthM:t.leafWidth,leafDensity:t.leafDensity,
    barkSRGB:t.woodColor,foliageSRGB:t.color});
}

export function treeStructuralVariant(recipe:TreeSpeciesRecipe,variant:number){
  if(!Number.isInteger(variant)||variant<0||variant>=TREE_VARIANT_COUNT)throw new Error('Tree variant is outside the bounded pool');
  const u=(channel:string)=>unit(recipe.version,recipe.speciesId,recipe.sourceFingerprint,variant,channel);
  const heightScale=.94+.12*u('height'),crownScale=.93+.14*u('crown');
  return Object.freeze({variant,branchSeed:hash(JSON.stringify([recipe.version,recipe.speciesId,variant,'branches'])),
    heightM:recipe.heightM*heightScale,crownWidthM:recipe.crownWidthM*heightScale*crownScale,
    trunkDiameterM:recipe.trunkDiameterM*heightScale,
    branchCount:Math.max(3,Math.round(recipe.branchCount*(.9+.2*u('branches')))),
    branchAngleRad:recipe.branchAngleRad+(.08*u('angle')-.04),
    curvature:recipe.curvature+(.08*u('curve')-.04),
    // Leaves keep their species dimensions when the whole tree grows taller.
    leafLengthM:recipe.leafLengthM,leafWidthM:recipe.leafWidthM,
    leafDensity:Math.min(1,recipe.leafDensity*(.94+.12*u('density')))});
}

/** Cheap per-instance shader parameters. Tints multiply separate bark/leaf
 * masks; they never choose a new topology or a new species. */
export function treeInstanceAppearance(recipe:TreeSpeciesRecipe,cellId:string){
  if(!cellId)throw new Error('Canonical cell id is required');
  const u=(channel:string)=>unit(recipe.version,recipe.speciesId,cellId,channel);
  return Object.freeze({variant:Math.floor(u('variant')*TREE_VARIANT_COUNT),
    barkBrightness:.92+.16*u('bark'),foliageBrightness:.9+.2*u('foliage'),
    windPhase01:u('wind'),textureVariant:Math.floor(u('texture')*4)});
}

export function treeGeometryCacheKey(recipe:TreeSpeciesRecipe,variant:number,lod:0|1|2,assetVersion=TREE_ASSET_VERSION){
  if(![0,1,2].includes(lod)||!assetVersion)throw new Error('Tree asset version and valid LOD are required');
  treeStructuralVariant(recipe,variant);
  return JSON.stringify([recipe.version,assetVersion,recipe.speciesId,recipe.sourceFingerprint,variant,lod]);
}
